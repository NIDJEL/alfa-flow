# Financial Twin Lite / прозрачный baseline

Это детерминированная учебная модель, не ML, не гарантия и не confidence score.
Модельная дата зафиксирована: 22 октября 2026; исторические полные месяцы April–September.
Начальная точка — синтетический **текущий** баланс на дату модели.

1. Месячные агрегаты строятся из просматриваемых транзакций. Own-account internal_transfer
   не считается выручкой. One-off credit не используется как регулярная выручка.
   Debit refund уменьшает sales, а не учитывается повторно как ordinary operating expense.
2. Forecast revenue — медиана суммарных исторических credits по дате. Дневные expenses сперва
   суммируются по дате (включая existing debt), затем медиана по дню месяца.
   Это сохраняет календарь регулярных обязательств и не теряет второй платёж того же дня.
3. Будущие синтетические commitments добавляются отдельно: 1 100 000 ₽ 2 ноября.
4. `balance[t] = current_balance + Σ(inflow−operating−existing_debt−commitments)
   + disbursement − Σ(new_loan_payments)`.
5. Hypothetical disbursement на следующий день; новый платёж — раз в календарный месяц,
   начиная со следующего месяца после этой даты. Выдача не является выручкой.
6. Без кредита и со сценарием используют один и тот же baseline. Возвращаются первая дата
   отрицательного остатка и минимум для обеих кривых.
7. Расчёт 30/60/90 дней; при истории <3 месяцев points пусты и явно insufficient history.
   После CSV import месяц считается достаточно покрытым только при ≥20 различных дней операций;
   три одиночные строки за три месяца не создают ложную достаточную историю.
8. Lower/upper — ±15% накопленной ожидаемой выручки; **эвристика**, не ML confidence interval.
   В UI раскрыты допущения; диапазон возвращён API, но отдельная заливка uncertainty band не отображается.

Seed маркирует регулярные категории rent/payroll/operations/debt. Это не универсальное
распознавание банковских merchant patterns. Операции October до as-of отсутствуют намеренно;
current balance задан отдельно. Модель не восстанавливает реальные обороты за пропущенный период.
One-off sales/возвраты не предсказываются. Изменения сезонности после истории не моделируются.
Для реального банка нужны business calendar, reconciled ledgers, доходность/сезонность и backtesting.

Unit reconciliation проверяет `funded − baseline = principal − реальные scheduled payments`,
исключение own-account transfers, monthly totals, возвраты и ветку недостаточной истории.
